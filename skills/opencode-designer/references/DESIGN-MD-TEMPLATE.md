# DESIGN.md Template

Use this template when creating or updating `DESIGN.md` for a project. This file is the canonical structure; `/init-harness` writes this exact 9-section shape when seeding a project.

The 9 sections map to the Open Design catalog schema and to the executor lane rules added in `agents/frontend.md`, `agents/mobile.md`, `agents/fixer.md`, `agents/visual-asset-generator.md`, and `agents/design-system-engineer.md`. If a section is empty, the grader at `scripts/design-md-grader.py` returns `NEEDS_FIX`.

## Structure

```markdown
# [Project Name] Design System

> Category: [Product category, audience, platform]
> Source: Generated by `/init-harness` or `python3 ~/.config/opencode/scripts/init-design-system.py --project-root .` (or `--system <slug>` when picking from Open Design catalog).
> Provenance: cite the catalog or `awesome-design-md` source used; otherwise mark "first-principles".

## Visual Theme & Atmosphere
Product personality, visual mood, density, tone, what the UI should feel like in use, and what it must NOT feel like.

## Color Palette & Roles
Semantic roles: background, surface, text, muted text, border, primary accent, secondary accent, success, warning, destructive, focus, data-vis. Prefer existing tokens/classes/variables when found.

## Typography Rules
Heading, body, label, caption, numeric, code/mono usage. Include scale, weight, line-height, tracking, and when display type is appropriate.

## Component Stylings
Buttons, inputs, cards, navigation, tables/lists, dialogs/drawers, feedback surfaces, empty states, icons, imagery, charts. Include important variants and states.

## Layout Principles
Grid, max widths, spacing rhythm, section density, responsive breakpoints, sticky/fixed behavior, content hierarchy across mobile/tablet/desktop.

## Depth & Elevation
Border, shadow, layering, overlays, focus rings, hover/active depth, when flat vs elevated surfaces should be used.

## Do's and Don'ts
Concrete project-specific rules, anti-generic UI rules, icon/image rules, copy/metric rules, and what must never be introduced without approval.

## Responsive Behavior
Mobile-first rules, navigation changes, CTA placement, data display adaptation, form behavior, image crops, touch target expectations, reduced-motion expectations.

## Agent Prompt Guide
Direct instructions for future coding/design agents: which files/tokens/components to read first, how to apply this design system, when to reuse/extend/create, when to ask questions, when to run visual validation, how to report deviations. Also state the downstream ownership chain for substantial UI work.
```

## Usage

1. Create: copy this template to project root as `DESIGN.md` (or run `/init-harness`).
2. Customize: fill in project-specific values from research, references, or existing UI.
3. Maintain: update when design decisions change.
4. Validate: run `python3 ~/.config/opencode/scripts/design-md-grader.py --project-root .` and confirm exit 0.

## Section authority

The 9 sections correspond to the 9-section mental model that executor lanes use to translate `DESIGN.md` into implementation rules. Each section maps to specific implementation rules:

- `Visual Theme & Atmosphere` -> product surface tone, density, navigation chrome, hero composition.
- `Color Palette & Roles` -> token/utility class usage and `must_avoid_token` checks.
- `Typography Rules` -> scale, weights, tracking, and display-type eligibility.
- `Component Stylings` -> component variants, states, and accessibility.
- `Layout Principles` -> grid, container widths, section spacing, sticky behavior.
- `Depth & Elevation` -> border, shadow, overlay, focus ring rules.
- `Do's and Don'ts` -> reject patterns, anti-AI-slop, content authenticity rules.
- `Responsive Behavior` -> mobile-first rules, navigation collapse, touch targets, reduced motion.
- `Agent Prompt Guide` -> which files/tokens to read, when to ask, when to validate visually, who owns each step.

## Integration with lanes

- `@designer`: reads `DESIGN.md` first, produces blueprint aligned with all 9 sections.
- `@design-system-engineer`: translates the 9 sections into tokens/primitives; mapping must be explicit.
- `@frontend` / `@mobile`: implements screens using the 9 sections as the source of truth.
- `@fixer`: bounded UI fixes must preserve the rules in the 9 sections.
- `@visual-asset-generator`: asset prompts must map back to the 9 sections.
- `@quality-gate`: validates the 9 sections are present, non-empty, and reflected in implementation.

## Minimal valid example

```markdown
# Acme Dashboard Design

> Category: Internal SaaS dashboard for ops teams.
> Source: first-principles, no catalog citation yet.

## Visual Theme & Atmosphere
Calm, data-dense, never decorative. Optimized for analysts and admins.

## Color Palette & Roles
- Primary: #2563eb
- Surface: #ffffff
- Muted text: #64748b
- Success: #10b981
- Warning: #f59e0b
- Destructive: #ef4444

## Typography Rules
- Font: Inter, system-ui
- H1: 32/40 700, H2: 24/32 600
- Body: 16/24 400, Small: 14/20 400

## Component Stylings
- Button: primary (filled blue), secondary (outline), ghost (text)
- Card: white bg, 8px radius, 16px padding, 1px border #e2e8f0

## Layout Principles
- Max width 1280px, 12-col grid on desktop
- Section padding 48px desktop / 32px mobile

## Depth & Elevation
- Flat by default; 1 shadow level for floating dialogs only
- Focus ring: 2px primary, 2px offset

## Do's and Don'ts
- Do show real data; never invent metrics.
- Don't use card spam or decorative imagery.

## Responsive Behavior
- Mobile-first; nav collapses to bottom sheet below 768px.
- Touch targets >= 44x44.

## Agent Prompt Guide
- Read `DESIGN.md` first; then `.opencode/design-system/registry.md` if present.
- `@frontend` implements, `@designer` reviews, `@quality-gate` final signoff.
```
